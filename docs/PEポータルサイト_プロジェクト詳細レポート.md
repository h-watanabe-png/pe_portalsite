## 1. プロジェクト概要

### 1.1 プロジェクトの目的

PEポータルサイトは、社内のシステムチームと経理部門への依頼を一元管理し、以下の課題を解決することを目的としています：

1. **依頼の見える化**: 誰が、いつ、何を依頼したかを明確にする
2. **処理状況の追跡**: 依頼の進捗状況をリアルタイムで確認できる
3. **情報の構造化**: Slackでの問い合わせを分析し、構造化されたフォームで依頼を受け付ける
4. **ナレッジの蓄積**: 過去の対応履歴やFAQを検索・参照できる

### 1.2 開発アプローチ

本プロジェクトは、**Cursor AIエージェントによる完全自動実装**を採用しています。これにより：

- 開発工数を大幅に削減
- 一貫性のあるコード品質を維持
- 迅速なプロトタイプ開発と改善サイクルを実現

### 1.3 技術スタック

- **バックエンド**: Google Apps Script (GAS)
- **データストレージ**: Google Spreadsheets
- **フロントエンド**: HTML5, CSS3, JavaScript (Vanilla)
- **開発ツール**: Cursor AI, clasp, Git

## 4. 実装内容

### 4.1 コア機能の実装

#### 4.1.1 スナップショットキャッシュシステム

**目的**: GASの制約（6分の実行時間制限、API呼び出し制限）を回避し、一般的なシステム並みの高速レスポンスを実現

**実装内容**:
- 手動更新によるスプレッドシートのデータをキャッシュに保存（ロック制御による同時更新防止）
- ダッシュボードや検索でキャッシュを優先使用
- キャッシュ状態の可視化（インジケーター表示）
- 古いキャッシュの場合は更新ボタンを表示
- 自動更新トリガーを削除し、手動更新のみの運用に変更（ユーザーが更新タイミングを制御）

**効果**:
- ダッシュボード読み込み: 2-3秒 → **0.1-0.3秒**
- 検索処理: 1-2秒 → **0.1-0.2秒**
- ユーザーが更新タイミングを制御できる
- 不要な自動更新によるリソース消費を削減

#### 4.1.2 締日管理機能

**目的**: 請求書関連の締日（毎月15日）に間に合うよう、ユーザーと担当者の負担を最小限に

**実装内容**:
- 締日計算ロジック（当月15日/翌月15日/指定日）
- 締日アラート機能（超過/緊急/警告/通常）
- 締日リマインダー（7日前、3日前、当日）
- 自動優先度設定（締日までの残り日数に応じて）

**効果**:
- 締日超過のリスクを大幅に削減
- ユーザーが締日を意識せずに依頼できる

#### 4.1.3 自動仕分け機能

**目的**: Slackでの問い合わせを分析し、適切な担当（システムチーム/経理）に自動仕分け

**実装内容**:
- キーワードパターンマッチング
- 信頼度スコアの計算
- 信頼度が低い場合はユーザーに確認を求める
- 自動仕分けの精度確認UI（「この担当で合っていますか？」ボタン）
- フィードバックデータの蓄積と分析

**効果**:
- 依頼の誤送信を防止
- ユーザーの入力負担を軽減
- フィードバックデータの蓄積により、自動仕分け精度の継続的改善が可能

#### 4.1.4 ナレッジベース機能

**目的**: 過去の対応履歴やFAQを検索・参照し、繰り返しの問い合わせを削減

**実装内容**:
- 全文検索機能
- タグ付けによる分類
- ユーザー自身がナレッジを追加・更新可能
- 関連依頼との紐付け
- 検索結果の評価機能（👍/👎ボタン）

**効果**:
- 繰り返しの問い合わせを削減
- ナレッジの蓄積により、対応品質の向上
- フィードバックデータの蓄積により、検索精度の改善が可能

### 4.2 パフォーマンス最適化

#### 4.2.1 キャッシュ戦略

- **スナップショットキャッシュ**: 手動更新（ロック制御による同時更新防止）
- **通常キャッシュ**: 60秒の有効期限
- **データ更新時の自動無効化**: 常に最新データを保証
- **キャッシュ状態の可視化**: ヘッダーにインジケーター表示、古い場合は更新ボタンを表示

#### 4.2.4 データアーカイブ戦略

- **自動アーカイブ**: 完了して1年以上経過した依頼を自動的にアーカイブ用スプレッドシートに移動
- **月1回の自動実行**: 毎月1日 午前2時に自動実行（トリガー設定可能）
- **ドライラン機能**: アーカイブ対象を事前確認可能
- **メインシートの軽量化**: データ量増加によるパフォーマンス劣化を防止

#### 4.2.2 バッチ処理

- 複数のデータを一度に取得（バッチリクエスト）
- 一括書き込みによるAPI呼び出しの削減
- ページネーション対応

#### 4.2.3 非同期処理

- 長時間処理は非同期で実行
- ユーザーは処理完了を待たずに他の操作が可能

### 4.3 セキュリティ・運用面の考慮

#### 4.3.1 認証・認可

- Google OAuth認証によるアクセス制御
- ホワイトリスト方式のユーザー管理
- アクセスログの記録

#### 4.3.2 エラーハンドリング

- 指数バックオフ付きリトライ機構
- 明確なエラーメッセージの表示
- フォールバック機能（キャッシュがない場合は通常の方法で取得）
- トラブルシューティングガイドによる問題解決の迅速化

#### 4.3.3 ロック制御

- 同時更新を防止（LockService使用）
- 更新中フラグによる重複実行の防止
- タイムアウト処理

#### 4.3.4 データ管理

- データアーカイブ機能により、長期的なデータ増加に対応
- スプレッドシートデータ検証（プルダウン）により、データの整合性を確保
- タイピングミスを防止し、入力の高速化

## 6. 技術的な特徴・工夫

### 6.1 GAS制約の回避

**課題**: GASには6分の実行時間制限、同時実行数制限などの制約がある

**解決策**:
- **スナップショットキャッシュ**: 定期的にデータをキャッシュに保存し、API呼び出しを削減
- **チェックポイントパターン**: 長時間処理を分割し、複数回の実行に分ける
- **バッチ処理**: 複数のデータを一度に処理し、API呼び出しを削減
- **非同期処理**: 長時間処理は非同期で実行し、ユーザーを待たせない

### 6.2 スケーラビリティ

- **モジュール設計**: 機能ごとにモジュールを分割し、拡張性を確保
- **設定の外部化**: システム設定をスプレッドシートで管理し、コード変更なしで設定変更可能
- **フォーム設計の柔軟性**: スプレッドシートでフォームのスキーマを定義し、コード変更なしでフォームを拡張可能

### 6.3 保守性

- **コードの一貫性**: AI駆動開発により、一貫性のあるコード品質を維持
- **ドキュメント**: 各機能の設計書・実装ドキュメントを整備
- **エラーハンドリング**: 明確なエラーメッセージとログにより、問題の特定が容易
